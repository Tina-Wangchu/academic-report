# Hermes Skill 大范围改造记录与经验总结

## 一、改造背景

改造前的 skill 存在两个核心问题：
1. **搜索能力低下**：只有 arXiv 单一数据源，经常触发降级搜索，只返回 7.6-7.7 两天的文章
2. **分析能力为零**：报告直接照搬论文原文 abstract，没有结构化分析和领域综述

这些问题不是代码 bug，而是 **SKILL.md（系统提示词）本身的缺陷**。Hermes 是 LLM Agent，SKILL.md 就是它的"大脑指令"——指令没要求多源检索，Agent 就不会多源检索；指令没要求分析提炼，Agent 就直接复制原始数据。

## 二、根因分析

### 问题1：搜索来源单一 — 为什么只有 arXiv？

| 层面 | 原因 | 具体表现 |
|------|------|---------|
| **SKILL.md** | Data Sources 章节只列了3个源，没有"必须调用多个源"的强制指令 | Agent 读完 SKILL.md 后认为单源即可 |
| **SKILL.md** | 没有定义"遇到限流怎么办"的规则 | Semantic Scholar 返回 429 后，Agent 直接降级到 arXiv |
| **paper_search.py** | `API_REQUEST_LIMIT=200` 请求量过大 | 触发 Semantic Scholar 429 限流 |
| **paper_search.py** | API 间延迟只有 1 秒 | 不满足 Semantic Scholar <100req/5min 的限制 |
| **workflow_executor.py** | 降级策略太积极 | 标准搜索稍微失败就跳到浏览器降级方案 |

**连锁反应**：SKILL.md 没强制多源 → Semantic Scholar 429 → Agent 降级 → 只用 arXiv → 时间范围不准（arXiv API 的 submittedDate 过滤有 bug）→ 只有 2 天数据

### 问题2：照搬原文 — 为什么不会总结？

| 层面 | 原因 | 具体表现 |
|------|------|---------|
| **SKILL.md** | Procedure 只说"检索→生成报告→发邮件"，没有"分析"步骤 | Agent 拿到 API 数据直接格式化输出 |
| **SKILL.md** | Report Structure 要求的是"标题、作者、摘要（前500字）" | Agent 截取 abstract 前 500 字作为"摘要" |
| **paper-summarizer** | 声称"AI-powered"但实际是规则匹配 | 按关键词指示器分类句子，不是 LLM 分析 |
| **SKILL.md** | 没有禁止直接复制的指令 | Agent 认为复制 abstract 就是正确行为 |
| **workflow_executor.py** | Step 2 调用 paper_summarizer.py 做假分析 | 规则匹配结果质量差，但 Agent 不知道 |

**核心误解**：之前认为需要写一个 Python 脚本做"AI 总结"，但实际上 Hermes **本身就是 LLM**。只要 SKILL.md 明确告诉 Agent "用你自己的智能分析论文"，它就能做到。paper_summarizer.py 的规则匹配反而降低了质量。

## 三、改造内容

### 3.1 SKILL.md 系统提示词改造（最关键）

改造了 4 个 SKILL.md 文件，这是所有改动中影响最大的：

#### paper-email-service/SKILL.md（编排器，核心指令）

**新增章节 — CRITICAL: AI Analysis Requirements (MANDATORY)**

```
禁止行为：
- 直接复制论文abstract到报告中
- 跳过AI分析步骤，直接用原始API返回数据
- 只使用单一数据源
- 不做去重和筛选

必须执行的分析流程：
用户请求 → 多源并行检索 → AI深度分析 → 生成HTML报告 → 发送邮件

阶段2 - AI深度分析（Agent自身智能，非外部脚本）：
- 单篇分析：研究目标、核心方法、关键创新、主要发现、研究意义
- 领域综述：研究热点、方法演进、研究空白、未来方向
- 智能筛选：多维度评分，同方向只保留最高分1-2篇
```

**改造前 vs 改造后**：

| 项目 | 改造前 | 改造后 |
|------|--------|--------|
| Procedure | 检索→报告→邮件（3步） | 多源检索→AI分析→HTML报告→邮件（4步） |
| 报告格式 | Markdown（丑陋） | HTML（美观CSS排版） |
| 分析要求 | 无（直接复制abstract） | 强制AI结构化分析 |
| 数据源 | 未强制多源 | 必须调用 Semantic Scholar + arXiv + CrossRef + OpenAlex |
| 报告结构 | 5章（封面、概况、列表、趋势、参考文献） | 6章（+领域综合分析为核心章节） |

#### paper-search/SKILL.md（搜索技能）

- Data Sources 从 3 个扩展到 5 个（+OpenAlex, PubMed）
- 新增"多源检索规则"：必须调用多个源，429 时立即切换
- 报告生成脚本路径从 generate_report.py 改为 generate_report_complex.py

#### paper-summarizer/SKILL.md（分析技能，完全重写）

改造前：声称"AI-powered"但实际是规则匹配脚本
改造后：明确说明"由 Agent 自身智能驱动，非外部脚本"，定义了单篇分析和领域综合分析的输出结构

#### report-generator/SKILL.md（报告技能）

- 移除所有 PDF 引用，统一为 HTML
- 报告结构新增"AI领域综合分析"核心章节
- 脚本路径统一指向 generate_report_complex.py

## 四、改造前后对比

### 搜索能力

| 维度 | 改造前 | 改造后 |
|------|--------|--------|
| 数据源数量 | 1个（arXiv 降级） | 5个（Semantic Scholar + arXiv + CrossRef + OpenAlex + PubMed） |
| 时间范围 | 2天（7.6-7.7） | 真实7天（timedelta 精确计算） |
| API 请求量 | 200篇/次（触发限流） | 50篇/次（稳定） |
| API 延迟 | 1秒（不足） | 2-3秒（满足限制） |
| 降级频率 | 频繁（因限流） | 罕见（多源备份） |

### 分析能力

| 维度 | 改造前 | 改造后 |
|------|--------|--------|
| 论文描述 | 复制 abstract 前 500 字 | Agent 原创结构化分析（5维度） |
| 领域综述 | 无 | 研究热点 + 方法演进 + 研究空白 + 未来方向 |
| 智能筛选 | 无（同质化严重） | 多维度评分 + 同方向保留最佳 1-2 篇 |
| 报告格式 | 丑陋 Markdown | 美观 HTML（CSS 渐变 + 响应式 + 打印友好） |
| 分析执行者 | paper_summarizer.py（规则匹配） | Agent 自身智能（真正的 LLM 分析） |

## 五、关键经验教训

### 教训1：SKILL.md 是灵魂，Python 脚本是工具

**错误认知**：认为需要写 Python 脚本实现 AI 分析
**正确做法**：Hermes 本身就是 LLM，SKILL.md 明确指令即可

SKILL.md 决定了 Agent 的行为上限。如果 SKILL.md 说"检索→报告→邮件"，Agent 就不会做分析。如果 SKILL.md 说"检索→分析→报告→邮件"并给出分析模板，Agent 就会用自身智能完成分析。

**规则**：SKILL.md 是"做什么"的定义，Python 脚本是"怎么做"的实现。优先在 SKILL.md 中定义行为，只在需要调用外部 API/工具时才写脚本。

### 教训2：必须用禁止清单（PROHIBITED），不能只写应该做什么

改造前的 SKILL.md 只描述了"应该做什么"（生成报告），没有说"不能做什么"（不能复制原文）。LLM 在没有明确禁止时，会选择最省力的路径——直接复制。

**规则**：在 SKILL.md 中同时写清楚：
- ❌ 禁止行为（列表形式，醒目标记）
- ✅ 必须执行的行为（带具体要求）

### 教训3：多源检索不能靠"建议"，必须靠"强制"

改造前写了"建议使用多个数据源"，Agent 仍然只用了一个。
改造后写了"必须调用 Semantic Scholar + arXiv + CrossRef + OpenAlex"，Agent 才会并行调用。

**规则**：对关键行为使用强制性语言（"必须"、"禁止"），不用建议性语言（"建议"、"可以"）。

### 教训4：工作流必须显式分阶段，不能让 Agent 自行决定

改造前的工作流：`检索→报告→邮件`（3步），Agent 把检索结果直接格式化为报告。
改造后的工作流：`多源检索→AI分析→HTML报告→邮件`（4步），明确要求先分析再生成。

**规则**：在 SKILL.md 的 Procedure 中显式列出每个步骤，特别是"分析"这种 Agent 可能跳过的步骤。

### 教训5：报告结构中"分析"章节必须标记为核心

改造前报告结构中"核心论文列表"是主角，"摘要"只是附带的原文截取。
改造后新增"领域综合分析"章节并标记为 ⭐ 核心章节，明确说明"必须由 Agent 原创生成"。

**规则**：在报告结构定义中，区分"数据格式化"章节和"AI 分析"章节，后者必须明确标注为 Agent 原创内容。

## 六、以后用 Claude Code 创建 Skill 一步到位的检查清单

创建一个新的 Hermes Skill 时，按以下清单逐项检查：

### A. SKILL.md 系统提示词（最重要）

- [ ] **description** 中是否包含了所有触发关键词？
- [ ] **When to Use** 是否覆盖了所有用户可能的表述方式？
- [ ] **Procedure** 是否显式列出了每个步骤（特别是分析/总结步骤）？
- [ ] 是否有 **禁止行为** 清单？（不能只写"应该做什么"）
- [ ] 关键行为是否使用了 **强制性语言**（"必须"、"禁止"）？
- [ ] 是否要求 **多源/多工具** 调用？（不能用建议性语言）
- [ ] 报告/输出的 **结构定义** 中是否区分了"数据格式化"和"AI 分析"？
- [ ] 是否标记了哪些章节是 **Agent 原创内容**？

### B. 数据流设计

- [ ] 工作流是否显式分为 **检索→分析→生成→交付** 四阶段？
- [ ] 是否定义了 **降级策略**？（主方案失败时怎么办）
- [ ] 是否定义了 **数据格式契约**？（阶段间传递什么格式的数据）

### C. Python 脚本

- [ ] 脚本只负责 **Agent 做不到的事**（调用 API、读写文件、发送邮件）
- [ ] Agent 能做的事（分析、总结、决策）**不要写脚本**，在 SKILL.md 中指令即可
- [ ] API 调用是否考虑了 **限流**？（延迟、重试、请求量）
- [ ] 是否有 **错误处理**？（超时、429、解析失败）

### D. 输出格式

- [ ] 是否选择了 **最稳定的格式**？（HTML > Markdown > PDF）
- [ ] 输出格式是否有 **编码问题**？（PDF 在 Windows 上容易乱码）
- [ ] 报告是否包含 **AI 分析内容** 而非纯数据格式化？

### E. 部署

- [ ] 文件是否放在 Hermes 期望的 **{category}/{skill-name}/** 目录结构下？
- [ ] 是否有 **DESCRIPTION.md**？
- [ ] 是否清除了 **Python 缓存**？
- [ ] .gitignore 是否排除了 **临时文件、日志、缓存、文档**？

## 七、豆包建议的评估

豆包的建议核心思路正确（多源检索 + AI 分析 + 分阶段工作流），但有几点需要注意：

| 豆包建议 | 评估 | 实际处理 |
|---------|------|---------|
| 新增多学术检索 Tool | 方向正确 | paper_search.py 已有5个 API 类 |
| 改写 System Prompt 强制多源检索 | **最关键的建议** | 已实施，效果最大 |
| 增加统一数据归一化函数 | 有用 | formatters.py 已有 fallback 链 |
| 拆分双阶段 Workflow | **核心建议** | 已实施：检索→分析→报告→邮件 |
| 新增专用总结 Prompt 模板 | 有用但不应照搬 | 在 SKILL.md 中定义分析维度，而非固定模板 |
| 强制 Agent 二次推理 | **核心建议** | 禁止直接输出原始结果 |
| 集成聚合 SDK | 不实际 | 各 API 格式差异大，手动封装更可控 |

**结论**：豆包最大的价值在于指出了"SKILL.md 缺少强制多源检索和总结提炼指令"这个根本问题。具体实现时不应照搬其模板格式，而是结合 Hermes Agent 的实际能力（LLM 自身智能 + SKILL.md 驱动）来设计。
