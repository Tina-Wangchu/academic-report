# Academic Report v1.0 vs v2.0 — 功能与实现差异对比

> 对比对象
> - **v1.0**：`v1.0/` 子目录（GitHub `v1.0-deprecated` 分支，已弃用）
> - **v2.0**：仓库根 `academic-report/`（GitHub `main` 分支，当前版本）
> - v1.0 为早期的失败版本：并没有需求文档化而是在和claude对话中进行修改内容沟通， 上下文长了之后（compact之后）就会丢失内容， claude很容易修改越来越偏：正确的方法在v2.0中落实，先撰写详尽的需求设计文档，然后初始化文件夹，在CLAUDE.md中要求每次修改时都要重新看一遍需求文档并且修改后同步跟新需求文档
>
> 本文档从**整体架构、模块逐一对照、模块间连接方式、关键能力（LLM/数据源/数据模型/调度/增量）、质量与工程化**等角度说明两者的功能与实现差异。

---

## 0. 一句话结论

| | v1.0 | v2.0 |
|---|---|---|
| 架构形态 | **多技能组合**：4–5 个独立 Hermes 技能 + 1 个编排技能，靠 `subprocess` 调子脚本、`JSON 文件/stdout` 传数据 | **单一技能统一流水线**：一个 `pipeline.py` 进程内顺序调用 6+ 个模块，共享 `Paper` 对象 |
| 数据模型 | 无类型 `dict`，各源字段不一致，靠 `DataFormatter` 临时规整 | 强类型 `Paper` / `SearchIntent` dataclass（25+ 字段） |
| 论文分析 | 名为「AI 摘要」实为**纯规则**关键词分桶，**全程无 LLM** | **真 LLM**（智谱 GLM）生成式「四要素」分析 + 规则兜底 + 缓存 + 全文补全 |
| 数据源 | S2 / arXiv / CrossRef（`urllib`，串行，无限流） | S2 / arXiv / **OpenAlex**（`ThreadPoolExecutor` 并行 + `RateLimiter`） |
| 报告 | PDF/HTML/MD 三套独立生成器，英文标题+中文要点，非双语 | 单一生成器产出 **Markdown+PDF**（PDF 由 MD 经 reportlab 转换），**中英双语**，按热点分组 + 四要素 + 奠基论文 |
| 调度 | 不是真调度器，委托外部 `hermes cron` | **进程内真调度器** `scheduler.py` + 每主题时间戳持久化 |
| 测试 | 散乱集成/冒烟脚本，无统一约定 | **273 个** pytest 单元测试，统一 `test_<module>.py` 约定，全离线 mock |
| 文档诚实度 | 大量文档-代码漂移（MCP/Google Scholar/AI 摘要/PDF 等均为「写了但没实现」） | 文档与代码严格同步（CLAUDE.md Rule 2），未实现项诚实标注「预留」 |

**v2.0 是对 v1.0 的全面重写**，不是增量改进：把「多技能 + 子进程 + 无类型 dict + 规则分析」的松散组合，收敛成「单技能 + 进程内 + 强类型 + LLM 分析 + 统一报告格式」的一体化流水线。

## 1. 整体架构对比

### v1.0 — 多技能组合（multi-skill composition）

```
paper-email-service-skill (编排技能)
   │  subprocess.run() 调用兄弟技能脚本
   │  数据经 JSON 文件 / stdout 跨进程传递
   ▼
paper-search   ──► report-generator   ──► email-sender
(paper_search.py)  (generate_report.py)   (send_email.py)
   ※ paper-summarizer 技能存在但【未被编排链路接入】
```

- **5 个独立 Hermes 技能**，每个是自己的 skill 目录 + `SKILL.md` + `scripts/*.py`。
- 编排技能 `paper-email-service-skill` 通过 [`workflow_executor.py:57-70`](v1.0/paper-email-service-skill/scripts/workflow_executor.py) 的 `_locate_skill_paths()` 计算兄弟目录，再 `subprocess.run([sys.executable, ...])` 调起，参数走命令行，结果走 stdout 或 `/tmp` 下的 JSON 文件。
- 仓库里这些技能**有重复副本**（`paper-skill/`、`skills/academic/`、顶层各一份），项目自身文档也承认这点。

### v2.0 — 单一技能统一流水线（single unified pipeline）

```
pipeline.run_pipeline(user_input)        ← 一个进程，一次调用
   │  直接 Python import，共享 Paper 对象
   ▼
IntentParser ─► PaperSearcher ─► PaperFilter ─► PaperAnalyzer+ReportGenerator ─► EmailSender
   │              (3源并行)       (打分+热点聚类)   (LLM四要素+APA+奠基)            (SMTP)
   └── 增量分支：timestamp_manager (每主题 last_run) + scheduler.py (进程内定时)
```

- **1 个技能** `academic-report`，`SKILL.md` 用 CRITICAL 指令要求 agent「只跑 `pipeline.py` 这一条命令，禁止自行检索/写报告/发邮件」。
- 全部模块在 `academic-report/scripts/` 下，进程内 `import` 调用，无子进程、无 JSON 文件中转。

### 连接方式根本差异

| 维度 | v1.0 | v2.0 |
|---|---|---|
| 进程边界 | 每个技能一个进程（`subprocess.run`） | 单进程，模块直接调用 |
| 数据载体 | JSON 文件（`/tmp/paper_email_service/`）+ stdout | 内存中的 `Paper` 对象 |
| 数据契约 | 隐式 `dict`，靠 [`formatters.py:17-74`](v1.0/paper-email-service-skill/scripts/utils/formatters.py) 规整（`abstract or summary`、`source or journal or venue`…） | 显式 `Paper` dataclass |
| 编排步骤 | 3 步（search→report→email；summarizer 未接入） | 6 步（意图→检索→筛选→分析→报告→邮件） |
| 路径解析 | `config_dir.parent.parent` 假设兄弟目录布局，本仓库布局下会解析错 | `SKILL.md` 写死**绝对路径**（因 `$HERMES_SKILL_DIR` 未设置） |

## 2. 模块逐一对照

### 2.1 检索模块（Search）

| 维度 | v1.0 [`paper_search.py`](v1.0/paper-skill/paper-search/scripts/paper_search.py) (953 行) | v2.0 [`paper_search.py`](academic-report/scripts/paper_search.py) (588 行) |
|---|---|---|
| 数据源 | Semantic Scholar、arXiv、**CrossRef** | Semantic Scholar、arXiv、**OpenAlex**（替换 CrossRef） |
| HTTP | `urllib.request` + `ssl._create_unverified_context()`（强制不校验证书） | `arxiv` 库 + `requests`（正常 TLS） |
| 并发 | 串行，每源间隔 1s | `ThreadPoolExecutor(max_workers=3)` 并行 |
| 限流 | 无统一限流对象 | `RateLimiter.wait_if_needed(source)` 按源限流 |
| 每源取数 | 固定池 **200 篇**（`api_request_limit=200`），与用户 `max_results` 无关 | 按 `intent.max_results`（默认从 config 取） |
| 去重 | 归一化标题 / `title:doi` | DOI 优先 + 标题，保留有 DOI 记录 |
| 日期精度 | 天级（`_filter_by_date`） | **天级 `published_date`** + 年级回退（增量过滤精确到日） |
| 查询语言 | 原样（中文直接搜，命中率低） | **中文→英文学术术语映射**（70+ 词），搜索始终用英文 |
| 字段规整 | 各源字段不一致（`summary`/`abstract`、`published`/`publicationDate`），arXiv 无引用量/DOI，CrossRef 无引用量/url | 统一映射到 `Paper` 字段；额外抓 `pdf_url`（全文补全用）、`tldr`（S2） |

> v1.0 文档/SKILL.md 声称「Google Scholar 兜底（爬虫）」「OpenAlex/PubMed/MCP 搜索」，但代码均**未实现**（见 §4）。

### 2.2 筛选与排序（Filter / Rank）

| 维度 | v1.0 [`quality_scorer.py`](v1.0/paper-skill/paper-search/scripts/quality_scorer.py) + [`representative_selector.py`](v1.0/paper-skill/paper-search/scripts/representative_selector.py) | v2.0 [`paper_filter.py`](academic-report/scripts/paper_filter.py) |
|---|---|---|
| 打分模型 | 0–100 分，5 维：引用 30 / 期刊 25 / **作者声誉 20** / 创新词 15 / 时效 10 | 优先级分：引用分层（≥100→+100 / ≥50→+50）+ 渠道分层（顶刊 90/顶会 80/SCI·EI 70/普通刊 50/预印本 30）+ `min(citation,50)` + 最新 +40 |
| 是否启用 | **可选**（`--enable-quality-filter` 旗标），默认按 API 相关性/引用/日期排序 | **流水线必经**步骤 |
| 聚类 | `representative_selector`：标题关键词 **Jaccard 相似度**（阈值 0.4）贪心聚类保多样性 | `classify_by_topic` 热点聚类（带查询+领域提示） |
| 质量过滤 | 无硬过滤 | `highly_cited` / `core_journal`（顶刊）/ 剔除预印本 / `min_citation_count` 可配 |
| 作者声誉 | 5 人硬编码名单（Hinton/LeCun/Bengio/Ng/Jordan） | 无（避免硬编码偏置） |

### 2.3 分析模块（Analysis）—— **最大差异**

| 维度 | v1.0 [`paper_summarizer.py`](v1.0/paper-skill/paper-summarizer/scripts/paper_summarizer.py) + [`enhanced_analysis.py`](v1.0/paper-skill/report-generator/scripts/enhanced_analysis.py) | v2.0 [`llm_analyzer.py`](academic-report/scripts/llm_analyzer.py) (589 行) + [`paper_analyzer.py`](academic-report/scripts/paper_analyzer.py) |
|---|---|---|
| 是否用 LLM | **否**。`_call_ai_summarizer` 名为 AI，实为 `_enhanced_rule_based_summary` | **是**。智谱 GLM（Anthropic 兼容端点 `/v1/messages`，复用 `ANTHROPIC_AUTH_TOKEN`） |
| 摘要/要点 | 按关键词把摘要句子分进 4 桶（problem/method/finding/contribution），各取 ≤2 句，凑 ~300 词 | **四要素生成式分析**：解决的问题 / 已有方案（引用先前工作）/ 新方案 / 效果及局限性 |
| 兜底 | 无 | LLM 失败 → 规则 `StructuredExtractor`（强弱标记打分）→ 缓存命中 |
| 无摘要论文 | 无法处理 | **自动抓全文**（arXiv PDF→`fitz` 文本 / OpenAlex OA PDF / Unpaywall / HTML 抽取关键段）喂给 LLM |
| 闭源论文 | 留空或规则占位 | **标注检索链接**（DOI / Google Scholar），`analysis_source="unavailable"`，不浪费 LLM 调用 |
| 趋势/缺口 | `enhanced_analysis.py`：关键词频次 + 硬编码主题桶 + 7 个学科交叉词对 + emoji 模板话 | 从**本次收录论文**派生（高频关键词、年份分布），避免空泛套话 |
| 奠基论文 | 无 | `CitationFinder` 查每个热点 1–3 篇奠基性参考论文 |
| 引用格式 | 无 | APA 7th（≤20 作者全列 + Oxford 逗号，>20 用省略号） |
| 限流/重试 | 无（不发网络） | 429/5xx/超时 **指数退避重试**（3/8/15/25s）+ `min_interval=1.5s` 节流 |
| 缓存 | 无 | `~/.hermes/llm_cache_four_element.json`（SHA1(doi\|title) 键，原子写） |

|---|---|---|

| 时间戳更新时机 | 无明确「仅成功后更新」语义 | **仅邮件发送成功后**更新（`--no-email` 时生成成功即更新，供本地测试）；空增量跳过且不更新 |
| 状态稳定性 | 非 DOI 的 paper id 用 Python `hash()`（进程级盐，**跨运行不可复现**） | last_run 存 ISO 时间戳，`fromisoformat` 回环，稳定 |

## 3. 模块间连接 —— 数据流详解

### v1.0 的连接（跨进程、无共享模型）

```
[orchestrator] subprocess(paper_search.py --output-format json)
     └─► stdout 解析回 list[dict]
         └─► DataFormatter.format_paper_data(dict)   # 规整字段名漂移
[orchestrator] dump → /tmp/papers.json
     └─► subprocess(generate_report.py --input papers.json --output report.pdf --format pdf)
[orchestrator] write email_body.txt + 报告路径
     └─► subprocess(send_email.py --attachment report.pdf)
```

要点：
- **三道进程边界**，每道都有 JSON 序列化/反序列化开销与字段漂移风险。
- 无共享 `Paper` 类，[`formatters.py:43-46`](v1.0/paper-email-service-skill/scripts/utils/formatters.py) 靠 `paper.get('source') or .get('journal') or .get('arXiv') or .get('venue')` 这种 fallback 桥接不同 API 的字段名。
- **`paper-summarizer` 技能存在但编排器从不调用**（其 SKILL.md 描述的手动 3 步集成与实际编排不符）。

### v2.0 的连接（进程内、共享对象）

```
pipeline.run_pipeline(input)
  intent = IntentParser().parse(input)           # SearchIntent
  papers = PaperSearcher().search(intent)         # List[Paper]（3源并行+去重）
  filtered = PaperFilter().filter_and_sort(papers, intent)
  classified = PaperFilter().classify_by_topic(filtered, ...)
  report = ReportGenerator(filter, analyzer).generate_report(filtered, intent, fmt)
                                  └─ 内部：PaperAnalyzer 填四要素(APA/奠基) + 渲染
  EmailSender().send_report(report_path, recipient, subject)
```

要点：
- **零进程边界**，`Paper` 对象贯穿始终，类型安全、字段统一。
- `ReportGenerator` 把「分析 + 聚类 + 奠基 + 渲染」**委托**给 `PaperFilter` / `PaperAnalyzer`，自身只管编排与格式（避免 v1.0 三套生成器各写一遍分析逻辑的重复）。
- 增量分支在主流程内条件触发，读 `timestamp_manager` → 设窗口 → 客户端天级过滤 → 成功后更新时间戳，**不引入额外进程或文件中转**。

## 4. 关键能力对比（实现 vs 文档）

| 能力 | v1.0 | v2.0 |
|---|---|---|
| **LLM 分析** | ❌ 文档称「AI 摘要」，代码纯规则（`paper_summarizer.py:62-71` 直接走规则分支） | ✅ 真 LLM（智谱 GLM），四要素生成式，带兜底/缓存/重试 |
| **MCP 工具** | ❌ 文档（`MCP_SEARCH_GUIDE.md`）描述 `mcp_search_integration.py`，**该文件不存在**，文档自承「模拟 MCP」 | — 不使用 MCP，搜索直连 API（诚实，不夸大） |
| **OpenAlex** | ❌ 仅出现在 MCP 文档，无代码 | ✅ 已接入（含 `abstract_inverted_index` 重建摘要、`best_oa_location` 取 PDF） |
| **PubMed** | ❌ SKILL.md 列为「扩展愿望」 | — rate_limiter 已配限流，Searcher 未接入（诚实标注「预留」） |
| **CrossRef** | ✅ 已接入 | — 未接入（被 OpenAlex 替代） |
| **Google Scholar** | ❌ 文档/文档字符串称「兜底爬虫」，无代码 | — 不使用 |
| **全文补全（无摘要论文）** | ❌ | ✅ arXiv PDF→fitz / OpenAlex OA / Unpaywall / HTML |
| **闭源论文标注** | ❌ 留空 | ✅ 标 DOI/Scholar 检索链接 |
| **双语报告** | ❌ 英文标题 + 中文要点混排 | ✅ CN/EN 双语 |
| **四要素** | ❌ 仅关键词分桶（结构近似但未标注四要素） | ✅ 显式四要素 |
| **APA 7th 引用** | ❌ | ✅ |
| **奠基论文** | ❌ | ✅ 每热点 1–3 篇 |
| **进程内定时** | ❌ 委托 `hermes cron` | ✅ `scheduler.py` |

## 7. 为什么 v2.0 取代 v1.0

1. **架构收敛**：v1.0 的「5 技能 + subprocess + JSON 中转」带来进程开销、字段漂移、路径解析脆弱（`config_dir.parent.parent` 假设布局）、文档-代码漂移（代码发 PDF、SKILL.md 说 Markdown）。v2.0 单进程共享对象，边界清晰、类型安全。
2. **分析能力质变**：v1.0 全程无 LLM，所谓「AI 摘要」是关键词分桶；v2.0 接入智谱 GLM 做真生成式四要素分析，并解决无摘要（全文补全）和闭源（标注检索链接）两个真实痛点。
3. **报告专业化**：v1.0 三套生成器 + 非双语 + 无四要素/奠基/整体分析；v2.0 单一生成器 + 双语 + 严格对齐 `报告格式设计.md` 的热点分组结构。
4. **调度真实可用**：v1.0 委托外部 `hermes cron`、状态用不可复现的 `hash()`；v2.0 进程内调度 + 稳定时间戳 + 仅成功后更新 + 空增量跳过。
5. **工程化**：v1.0 散乱测试 + 重复目录 + 文档夸大；v2.0 273 离线单测 + 单一目录 + 文档强制同步 + 未实现项诚实标注。
